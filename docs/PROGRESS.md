## Work log

### Phase 0: scaffolding and data

Built:
- Repo layout, `config.py` (everything from environment variables), `schemas.py` (the spec's
  models), `audit.py` (append-only SQLite log), `Makefile`, project rules in
  `.cursor/rules/authpilot.md`.
- Two payer policies as markdown with numbered sections: lumbar spine MRI (PA-RAD-014) and
  adalimumab for RA (PA-RX-207). Thresholds live in the policy text, so changing a policy
  changes behavior without code changes.
- Seeded case generator: 60 dev cases (seed 1001) and 40 sealed cases (seed 2002), half per
  procedure, with clean, missing, ambiguous, contradictory, distractor and deny-then-appeal cases.

Verified: generation is byte-identical for a seed, every label span equals
`chart[doc_id][start:end]`, every hard-case type appears in both splits.

### Phase 1: core agent pieces

Built:
- `llm.py`: one `complete()` with four modes (stub, replay, record, live), a request-hash cache,
  retries with exponential backoff, and token and latency logging.
- `stub_llm.py`: a deterministic offline model that reads the same prompts and answers through
  the same tool schemas, so everything runs without a key (your choice at the start).
- Tools `get_patient_record`, `search_policy` (BM25 over policy sections, written by hand) and
  `check_criteria` (criteria extraction by the cheap model, one validated call per criterion).
- `evidence.py`: the model returns quotes; code finds them verbatim and computes offsets.
- `eval/criteria_eval.py`: accuracy, per-status precision/recall/F1, false-met rate, citation
  validity, evidence overlap with labels, invalid-output rate, worst failures.

Finding that changed the plan: the stub scored 100% on dev, which showed the templates were too
regular to tell methods apart. This led to the data hardening below.

### Data hardening (between Phases 1 and 2)

- Every evidence phrasing now has a dev pool and a separate sealed pool; the sealed split also
  has its own document titles, section headings and drug names. A test checks that no sealed
  evidence template appears in dev.
- Harder sealed forms: abbreviations ("PT x 8 wks", "ROS: no B/B dysfunction"), durations in
  months, methotrexate intolerance described only as "nausea and elevated LFTs", tuberculin skin
  tests, imaging dates without "N months ago".
- After hardening, the stub dropped to 0.992 accuracy on dev with a 5% false-met rate, a real
  keyword failure that is kept visible on purpose.

### Phase 2: end-to-end flow

Built:
- Gap detection (every criterion not met becomes a gap with its policy section and reason).
- `request_missing_info` with a simulated clinic. The generator now gives about 70% of missing
  criteria a withheld document the clinic sends when asked; labels record whether the case
  should end approved or escalated.
- `draft_letter`: statements are kept only if a quote is verbatim and all numbers are supported.
- Mock payer (FastAPI, idempotent `POST /submit`, `GET /status/{id}`) with a rule-based reviewer
  that checks every criterion, that cited text is attached, and the content of number-based
  criteria (therapy duration, methotrexate, TB date window, DAS28 score), with thresholds read
  from the policy.
- `submit_request`, `check_status`, an `escalate` tool, the agent loop with caps, and the CLI.

Bug found and fixed: distractor cases were labeled "should escalate"; their criteria are met.

### Phase 3: loops, gate and fallbacks

Built:
- `gate.py`: approvals bound to the SHA-256 of the exact letter; the agent has no approval tool;
  the loop pauses at the gate, and `approve` or `resume` continues it (also across processes).
- `draft_appeal` and the denial loop: the appeal covers only the denied section, uses the same
  faithfulness checks, needs its own approval and its own idempotency key. A repeat denial for
  the same code, or a third denial, escalates.
- `fallback.py` with every spec rule, each logging a `fallback` audit event.
- 13 fault-injection tests (invalid output, invented evidence, low confidence, unclear, empty
  retrieval, empty policy, main model timeout, all models down, payer down on submit, lost payer
  response, payer down on status, connection error, garbage planner output) and 11 gate and
  appeal tests. All end in a safe state.

Result: with a simulated reviewer, 58 of 60 dev cases end where the labels say they should.

### Phase 4: frontend

First version: a plain single-page Streamlit dashboard, as the original spec asked.

Upgraded on request to a styled multi-page app (the spec's FRONTEND section and Phase 4 prompt
were rewritten to match):
- `app/dashboard.py`: entry point with `st.navigation` and four pages in `app/screens/`.
- **Home** (`screens/home.py`): landing page with the hackathon challenge and how AuthPilot
  covers its three example use cases, the problem, the solution flow with the human gate, the four
  ways the agent is autonomous, safety and trust, success targets (clearly marked as goals),
  future enhancements, and the full technology stack with built and planned items marked apart.
  Counts on the page (cases, tools, caps) are computed from the code, not typed in.
- **Workbench** (`screens/workbench.py`): status badges and counters, an approval panel that shows
  the exact letter, criteria cards colored by status with quoted evidence and source documents,
  a visual timeline from the audit log (raw table available), and tabs for the letter, the appeal
  letter and the clinic requests.
- **Escalation queue** (`screens/queue.py`): cards for every case waiting for a person, with an
  Open button that jumps to the workbench.
- **Results** (`screens/results.py`): saved runs with their metadata, metric cards, per-status and
  confusion tables, accuracy by case type, worst failures, and a stub warning banner.
- `app/ui.py`: one stylesheet and small components (hero, cards, badges, quotes, timeline, flow);
  every dynamic string is HTML-escaped (tested). `.streamlit/config.toml` holds the theme.
- Tests: view functions, HTML escaping, landing page sections, queue and results pages, and the
  run-then-approve flow through the workbench with Streamlit's headless test runner.
- Checked in a real browser: every page renders without errors, opening a case from the queue
  works, and approving in the workbench submits the case and shows "approved". Screenshots are in
  `docs/screenshots/`.

Bug found in the browser check and fixed: blank lines in letters let Markdown reformat the
numbered statements; letters are now rendered with explicit line breaks so they appear exactly
as submitted.

### Phase 5: full evaluation

Built (`authpilot/eval/`, run with `make eval`):
- `harness.py`: runs each case through the real agent loop with a simulated reviewer and turns
  the audit log into a record: initial verdicts and confidences, citations, gaps, initial
  decision, final outcome, denials and appeals, letter statistics, tool calls, tokens, latency,
  invalid outputs, and a safety verdict (every submitted span verbatim, no duplicate submission,
  nothing submitted without approval).
- `metrics.py`: per-criterion precision/recall/F1, false-met rate, citation validity, evidence
  overlap with labels, gap recall and precision, decision accuracy, final outcome accuracy,
  denial recovery, letter faithfulness, invalid-output rate, safe rate; mean and spread over
  repeated runs; percentile bootstrap intervals over cases (seeded); coverage vs accuracy.
- `baselines.py`: single-prompt baseline (one call, full policy and chart, same verbatim check)
  and a keyword-presence baseline (no model).
- Ablations as config switches: no retrieval, no citation check, no gap loop, no appeal loop.
- `perturb.py`: policy threshold 6 to 8 weeks (labels recomputed from stored facts), reworded and
  renumbered policies (`policies_reworded/`), noisy charts (reordered, abbreviated, padded, with
  every label span re-anchored), removed evidence documents, and the unseen procedure.
- Unseen procedure: a GLP-1 policy (PA-RX-310) whose criteria sit under "Eligibility
  requirements" and "Safety requirements", plus 10 seeded cases (`data/unseen_generator.py`).
  The agent has no code for it; the payer knows its own criteria.
- `faults.py`: payer down, corrupted model output and empty retrieval across all 60 dev cases.
- `run_all.py`: orchestrates everything, saves each run with its seeds, models and prompt version
  (`results/eval/<timestamp>_dev_stub.json`, `latest_dev_stub.json`, `latest_dev_stub.md`),
  and fails when any tracked score drops against the last comparable run. It refuses the sealed
  split without `--allow-sealed`.
- The Results page shows the latest full evaluation.

Findings (stub model, dev split):
- The loops earn their place: without the gap loop, final outcome accuracy falls from 0.967 to
  0.800; without the appeal loop, denial recovery falls from 0.60 to 0.
- Retrieval cuts tokens per case by about a third (5,093 vs 7,653 with the full policy).
- The keyword baseline is far worse (false-met 0.692, gap recall 0.308), so evidence-aware
  checking matters.
- The single-prompt baseline equals the agent on criteria with the stub, because both use the
  same heuristic; only a real model can separate them.
- Threshold change: all 9 affected verdicts flipped and all 21 unaffected stayed the same.
  Noisy charts and removed evidence cause no drop, and no removed criterion was guessed as met.
- Weak spots, both caused by the keyword stub: a 20.8-point drop on reworded policies, and 0
  on the unseen procedure (the stub cannot find its criteria, so every case escalates safely).
- All 180 fault-injection runs ended in a safe state.

Bugs found and fixed while building the evaluation:
- Documents the clinic sent during one run leaked into the next variant's chart (the baseline
  briefly looked worse than the agent for this reason). Received documents are now cleared after
  every run and baselines always start from the base chart.
- The threshold relabeling missed contradictory cases with under 8 weeks of therapy, which fail
  an 8-week rule under either reading. The agent had them right; the labels were fixed.
- Starting a run used to wipe in-memory chart overrides, which perturbations rely on. The EHR now
  keeps the base chart (file or override) separate from documents received later.
- A policy whose criteria cannot be read now escalates the case instead of crashing the loop.

## Decisions and deviations from the spec

| Topic | Spec or proposal | What was built | Why |
| --- | --- | --- | --- |
| Number of cases | Proposal: 60 (40/20) | 100 (60/40) | The markdown spec is the source of truth |
| Policy format | Proposal: PDFs | Markdown with numbered sections | Spec; easy to parse and perturb |
| Evidence offsets | Evidence has start/end | Model returns quotes, code computes offsets | Models are unreliable at character offsets; this keeps the verbatim check strict |
| Order schema | No date | Added `request_date` | Policies have time windows measured from the request date |
| Case state | Spec fields | Extra fields (approval, submissions, denial, queue, info requests) | Needed for the gate, appeals and resume |
| Unclear criteria | Gap loop or escalate | Escalate at once, with a summary | The spec's fallback rule says unclear means abstain and escalate |
| Escalation | Not in the tool list | `escalate` tool | The agent needs a safe way to stop |
| Deny-then-appeal | One scenario must be denied then approved | Payer first-level review accepts only clinical notes and lab reports (biologic policy 5.2); flowsheets count on appeal | Makes the denial follow from the written policy, not from a hidden rule |
| Payer review | Rule-based | Also checks the content of number-based criteria | Otherwise a false "met" with any real quote would be approved |
| Retrieval | BM25 | Hand-written BM25 | No extra dependency for about 30 lines |
| Temperature | temperature=0 | Sent via `extra_body` | anthropic 2.3.0 no longer has a temperature argument; can be turned off with `LLM_SEND_TEMPERATURE=0` |
| Payer hosting | FastAPI service | In-process by default, `make payer` for HTTP | Tests and demo need no server |
| Sealed split | Different seed | Different seed and held-out wording | A different seed alone reused the same sentences |
| Frontend | Spec: plain Streamlit, no styling; proposal: React or Next.js | Multi-page Streamlit with a custom theme and landing page; spec updated | Your choice: more polish for judges without a second codebase; React or Next.js stays a future enhancement |
| Repeats | 3 runs per case | 3 runs for the agent; 1 for baselines, ablations, perturbations and faults | Keeps a recorded Claude run affordable; `--runs` raises it |
| Keyword baseline | Keyword/rule baseline | Keyword presence (met if any criterion keyword appears) | The stub is itself a rule system, so a separate, simpler baseline gives a real comparison |
| Unseen procedure | Exists only as an adaptation test | GLP-1 policy with criteria under requirement headings and 10 cases; the payer knows its criteria | Tests adaptation honestly; the agent gets no code for it |
| Arabic letters | Proposal: Arabic letters (stretch) | Code-written Arabic templates around verbatim English quotes; English stays the submitted letter | A model translation could add or change clinical claims that no check can verify; templates keep the no-invented-facts guarantee |

## Known limitations and risks

- **No real model results yet.** All metrics come from the stub, which was written with
  knowledge of the templates.
- **Synthetic data is simpler than real charts.** Templates are finite; real notes are longer,
  messier and contain more conflicting information.
- **Simulated parts.** The clinic replies instantly and only supplies missing documents; it never
  clarifies ambiguous ones. The payer's rules are hard-coded per policy.
- **In-process payer** forgets submissions when the process exits; resuming a case that already
  has a submission needs `make payer`.
- **Letter faithfulness** checks quotes and numbers, not paraphrase drift in wording.
- **The stub is not adaptive.** It drops 20.8 points on reworded policies and cannot read the
  unseen procedure's policy at all. These are expected stub limits, not agent results.
- **Repeats show no variance with the stub** (it is deterministic); spread across runs becomes
  meaningful only with a real model.
- **No-citation-check ablation shows no effect with the stub**, because the stub never invents
  quotes; the effect of the check is shown by the fault-injection tests and needs a real model
  to measure at scale.
- **Arabic is limited to letters and the interface.** Clinical notes are English only, the Arabic
  letter quotes the chart in English, and the Arabic text has not been reviewed by a
  native-speaking clinician. In Arabic text, ISO dates display as day-month-year.
- **Not built yet:** role-based access in the web app, NPHIES-aligned message format.
- **Web app** runs in one process with the in-process payer; it has no login, and the reviewer
  name is typed in rather than taken from an account.
